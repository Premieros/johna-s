# Permissions UI Simplification Plan — 2026-09-23

## الهدف
تبسيط شاشة الأدوار والصلاحيات بدون تغيير نموذج الأمان الحالي أو RLS أو Permission-First أو قواعد الفروع.

## الوضع الحالي المؤكد
- الدخول إلى صفحة الصلاحيات محمي بـ `roles.permissions.manage`.
- غير Super Admin لا يستطيع منح Permission لا يملكها.
- تعديل الأدوار مقيد بالفروع المسموح بها.
- Super Admin هو التجاوز الضمني الوحيد.
- الحماية الخلفية موجودة في `guard_role_permissions()`.
- النظام الحالي يحتوي 111 صلاحية في 21 مجموعة، مع 69 علاقة اعتماد بين الصلاحيات.
- شاشة RolesTab تعرض حاليًا تفاصيل تقنية كثيرة: key / risk / kind / requires.
- المستخدم الذي لا يملك صلاحية أعلى منه لا يستطيع منحها، لكنها قد تظهر له كعنصر Disabled.
- المطلوب لاحقًا: إخفاء الصلاحيات غير المملوكة من العرض العادي، مع إبقاء الحماية الخلفية كما هي.

## قواعد التنفيذ
1. لا تعديل على RLS أو `guard_role_permissions()` إلا لو كشف اختبار حقيقي عن خلل.
2. لا تعديل على صلاحيات الطباعة أو POS runtime أو kitchen routing.
3. لا تغيير في أسماء الصلاحيات الحالية في المرحلة الأولى.
4. لا حذف لأي Permission قائمة.
5. لا منح صلاحيات تلقائيًا على Production.
6. كل تغيير يكون على فرع تطوير + PR + Full Verify قبل الدمج.
7. لا تعديل مباشر على `main`.

## المرحلة 1 — تبسيط العرض فقط
- تحويل الصفحة إلى عرض تشغيلي واضح:
  - القسم
  - اسم الوظيفة
  - مفتاح تشغيل/إيقاف
- إخفاء الأكواد التقنية مثل `pos.payment.take` من العرض العادي.
- إخفاء risk / kind / requires من العرض العادي.
- إبقاء التفاصيل التقنية داخل قسم "تفاصيل متقدمة" للـSuper Admin فقط.
- المستخدم غير Super Admin يرى فقط الصلاحيات التي يملك حق منحها.
- الصلاحيات الأعلى منه لا تظهر في الكتالوج أصلًا.
- الأدوار التي تحتوي صلاحيات أعلى من المانح لا تُكشف له بأسماء تلك الصلاحيات، وتبقى غير قابلة للحفظ حتى يتدخل Super Admin عند الحاجة.

## المرحلة 2 — تنظيم الأقسام
أقسام العرض المقترحة:
- نقطة البيع
- الطاولات والصالة
- المنتجات والفئات
- المشتريات
- المخزون
- المواد الخام والوصفات
- الإنتاج والهالك
- العملاء
- الموردون
- المصروفات
- المبيعات والمرتجعات
- الحسابات والخزائن
- الشيفتات واليوم
- التقارير
- المستخدمون
- الموافقات
- الإعدادات والفروع

## المرحلة 3 — ضمان عمل كل زر
اختبارات مطلوبة لكل عنصر قابل للنقر:
- تفعيل Permission يضيفها للحالة الصحيحة.
- إلغاء Permission يزيلها.
- الاعتمادات الأساسية تضاف تلقائيًا عبر `expandPermissionDependencies`.
- إزالة Permission أساسية تزيل التوابع عبر `removePermissionWithDependents`.
- زر الحفظ يكتب payload الصحيح.
- زر التراجع يعيد القيم المحفوظة.
- البحث يعرض البنود الصحيحة.
- تحديد مجموعة يعمل فقط على الصلاحيات التي يملك المانح حق منحها.
- قوالب POS لا تغير صلاحيات الطباعة الخلفية.
- مدير الفرع لا يستطيع تعديل Super Admin أو الأدوار العامة.
- المستخدم بدون `roles.permissions.manage` لا يستطيع فتح صفحة الصلاحيات.
- Backend يظل يرفض أي privilege escalation حتى لو تم تجاوز الواجهة يدويًا.

## المرحلة 4 — مراجعة الصلاحيات المجمعة
لا تنفذ ضمن المرحلة الأولى.
بعد استقرار الواجهة فقط تتم مراجعة البنود التي تجمع أكثر من وظيفة مثل:
- `pos.order.transfer` — نقل/دمج.
- `inventory.count.approve` — اعتماد/رفض/تطبيق.
- `settings.manage` — إعدادات عامة/طابعات/محطات.
- `accounts.manage`.
- `users.manage`.
- `purchases.manage`.

أي فصل لهذه الصلاحيات يحتاج Migration واختبارات Backend/RLS مستقلة.

## ملاحظات Production رُصدت أثناء الفحص
- لا توجد Permissions مجهولة/Legacy داخل أدوار Production الحالية.
- يوجد Drift اعتماد في دور `cap`: لديه `pos.kds_update` بدون `pos.kds_view`.
- يوجد Drift اعتماد في دور `cashier`: لديه `users.manage` بدون `users.view`.
- `production_manager` في Production حاليًا لديه 0 صلاحيات رغم وجود قالب افتراضي أوسع في الكود.
- لا يتم تصحيح هذه البيانات ضمن هذا الفرع إلا بموافقة منفصلة.
